# docs

여러 탭과 앱에 공통으로 적용되는 협업 규칙, 구조 원칙, 문서 정책, 샘플 자료 위치를 관리하는 폴더입니다. 이 문서는 특정 폴더 하나의 구현 설명이 아니라, 중앙화 코드 전체를 유지보수할 때 기준선으로 삼는 문서입니다.

## 이 문서의 역할

- 여러 탭에서 반복되는 구조와 작업 방식을 공통 규칙으로 정리
- 폴더별 README에 적어야 할 내용과 여기서만 다룰 내용을 구분
- 코드 변경 시 함께 점검해야 할 문서, 설정, `.gitignore` 원칙 정리
- 신규 기능 추가 시 기존 구현에서 어떤 패턴을 우선 따라야 하는지 안내

## 규칙의 우선순위

문서와 규칙은 아래 우선순위로 해석합니다.

1. 실제 코드와 실행 계약
2. 가장 가까운 폴더의 `README.md`
3. `docs/README.md`
4. 루트 `README.md`

즉, 이 문서는 공통 기준 문서이고, 특정 폴더에서만 유효한 예외는 해당 폴더 `README.md`에 명시하는 것을 원칙으로 합니다.

## 협업의 기본 원칙

### 1. 영향 범위가 명확한 구조를 우선한다

이 레포지토리는 탭 별 폴더 단위 분리를 기본 구조로 사용합니다. 이유는 탭 추가, 수정, 삭제 시 영향 범위를 폴더 단위로 명확하게 유지하기 위해서입니다.

- 탭 전용 로직은 가능한 한 탭 폴더 안에 둡니다.
- 유사 기능이 여러 탭에 있더라도, 먼저 탭별 구현으로 유지하는 편을 권장합니다.
- 단순히 비슷하다는 이유만으로 `app/common/`으로 올리기보다 수정 독립성과 영향 범위를 우선 고려합니다.

### 2. 코드 중복보다 물리적 분리를 우선한다

- 일부 코드가 중복되더라도 기능 단위로 물리적으로 분리하는 편을 기본값으로 둡니다.
- 특히 `page.py`, `panels/`, `features/`, `widgets/`는 탭별 맥락이 강하므로 섣불리 공통화하지 않습니다.
- 공통화는 “앞으로도 안정적으로 여러 탭이 함께 써야 하는 계약”일 때만 검토합니다.

### 3. 공통 코드는 인프라와 안정된 계약만 둔다

현재 `app/common/`에는 아래처럼 탭 공통 인프라 성격이 강한 코드가 들어 있습니다.

- `config/`: `ConfigManager`, 병렬 처리 설정 계산
- `panel_layout.py`: 3분할 기본 너비
- `shared_status_bar.py`: 상태 메시지와 진행률 형식
- `top_bar.py`: 상단 프로젝트 정보 UI
- `labels/`: 라벨 기준표 로더

새 코드를 `common/`으로 올릴 때는 “탭 간 재사용”보다 “공통 계약으로 묶어도 의미가 변하지 않는가”를 먼저 확인하는 편이 좋습니다.

### 4. 확장 포인트는 독립 단위로 관리한다

이 코드베이스에는 이미 확장 지점이 명확한 영역이 있습니다.

- `app/tabs/pre_parse/plugins/`: 검사 규칙 단위 플러그인
- `app/tabs/pre_parse/plugin_system/`: 플러그인 계약과 로더/러너
- `app/tabs/misc_tools/apps/`: 카드형 보조 앱 단위 확장

새 기능이 이런 성격에 맞으면 기존 확장 지점 안에서 해결하는 편이 유지보수에 유리합니다.

## 폴더 책임 구분

### `app/common/`

- 여러 탭에서 공통으로 쓰는 인프라 코드
- 설정, 상태 메시지, 라벨 로딩, 공통 레이아웃 기준

### `app/tabs/<tab>/`

- 탭 하나의 화면 구성과 실행 흐름 전체
- 탭 전용 데이터 처리, 미리보기, worker, 결과 가공

### `app/tabs/misc_tools/apps/<app>/`

- 메인 탭과 분리된 보조 앱 단위 기능
- 폴더 1개 = 앱 1개
- 앱 메타데이터와 진입점은 `__init__.py` 기준

### `app/tabs/pre_parse/plugins/`

- 독립 실행 가능한 검사 규칙 단위
- 플러그인 하나는 검사 규칙 하나를 기본 단위로 유지

### `config/`

- 추적되는 기준 설정 템플릿과 로컬 설정 파일 위치

### `label/`

- 라벨 ID, 표시명, 색상 기준이 되는 `*.xlsx` 자산 위치

### `docs/`

- 공통 규칙, 협업 기준, 참고 자료 위치
- 실행 코드가 직접 의존하지 않는 문서 자산 영역

## 구현 패턴에서 도출한 공통 규칙

### 1. 탭 구조는 `page.py`가 조립하고, 세부 역할은 분리한다

현재 `pre_parse`, `text_analysis`, `raw_data_analysis`는 모두 비슷한 역할 분리를 사용합니다.

- `page.py`: 탭 상위 조립, splitter 구성, signal 연결, 초기 상태 준비
- `panels/`: 좌/중/우 패널 UI
- `features/`: 조회, 실행, 스냅샷, worker, 결과 가공, 로그 처리
- `widgets/`: 이미지 뷰어, 툴팁, 버튼 같은 보조 위젯

즉, 화면을 그리는 코드와 실제 작업 흐름을 한 파일에 섞기보다, 조립과 실행을 분리하는 편을 기본 패턴으로 봅니다.

### 2. 3분할 탭은 공통 너비 기준을 사용한다

`pre_parse`, `text_analysis`, `raw_data_analysis`는 모두 `QSplitter(Qt.Horizontal)`와 `DEFAULT_THREE_PANEL_SPLITTER_SIZES`를 사용합니다.

- 기본 너비: 왼쪽 390, 가운데 780, 오른쪽 430
- 초기 진입 시 왼쪽 패널 폭을 잠깐 고정했다가 풀어주는 패턴 사용
- 왼쪽 패널: 입력/필터/실행
- 가운데 패널: 데이터/결과
- 오른쪽 패널: 미리보기/상세/통계

2분할처럼 다른 구성이 필요하면 허용하지만, 그 이유는 탭 README에 남겨 두는 편이 좋습니다.

### 3. 미리보기는 “선택 상태 → 우측 갱신” 흐름을 유지한다

현재 주요 탭은 모두 가운데 선택 상태가 바뀌면 오른쪽 미리보기가 바뀌는 구조를 사용합니다.

- 미리보기 캐시는 `.cache/` 아래 사용
- JSON, 이미지, 스냅샷 캐시를 분리해서 유지
- 페이지 선택과 미리보기 렌더링은 직접 결합하지 말고 중간 상태를 둠

이 흐름을 유지하면 미리보기 로직을 교체하거나 확장해도 영향 범위를 줄일 수 있습니다.

### 4. 상태 메시지는 공통 포맷을 사용한다

메인 창과 주요 탭은 `app/common/shared_status_bar.py`의 `format_progress_status(...)` 형식을 사용합니다.

권장 방식은 아래와 같습니다.

- 진행률이 있는 작업은 `format_progress_status(...)`를 사용
- 상태 문구는 짧고 반복 가능한 형식으로 유지
- 탭 내부 로그와 하단 상태바 문구가 크게 어긋나지 않게 맞춤

즉, 상태 메시지는 자유 문장보다 “무엇을 몇 개 중 몇 개 처리 중인지”를 우선 전달하는 편이 좋습니다.

### 5. 버튼과 툴팁은 의도 중심으로 작성한다

코드상으로 툴팁은 단순 제목 반복보다 설명 보강 용도로 쓰는 경우가 많고, `pre_parse`, `text_analysis`는 `InfoDotButton` + 커스텀 툴팁 패턴을 사용합니다.

권장 방식은 아래와 같습니다.

- 버튼 이름은 짧고 동사 중심으로 작성
- 툴팁은 버튼 이름 반복보다 영향 범위, 조건, 주의사항을 설명
- 같은 의미의 액션은 탭이 달라도 문구를 최대한 통일
  - 예: 조회, 실행, 중지, 미리보기, 저장, 내보내기

### 6. S3 작업은 스냅샷을 기준으로 읽고, 쓰기는 비교 후 반영한다

`pre_parse`와 `text_analysis`는 S3 조회 시 스냅샷을 준비하고, 일부 쓰기 작업은 최신본과 스냅샷을 비교해 불일치 시 중단하는 흐름을 사용합니다.

이 코드베이스에서 권장하는 원칙은 아래와 같습니다.

- 조회/검토는 가능한 한 스냅샷 기준으로 수행
- 실제 수정이 들어가는 작업은 최신본과 스냅샷 비교 기준을 둠
- 불일치 시 조용히 덮어쓰지 않고 중단 또는 경고
- 캐시와 원격 데이터의 역할을 README에 함께 설명

### 7. 병렬 처리 수는 공통 설정을 우선 사용한다

`pre_parse`, `text_analysis`, `raw_data_analysis`는 모두 `resolve_parallel_workers(...)`를 사용해 worker 수를 결정합니다.

권장 방식은 아래와 같습니다.

- worker 수를 탭마다 임의로 하드코딩하지 않음
- `total_tasks`를 넘겨 실제 작업 수보다 과도한 worker가 생기지 않도록 함
- 어떤 작업이 thread인지 process인지 이유를 코드와 README에서 설명 가능하게 유지

현재 코드 패턴상:

- 스냅샷/스캔처럼 CPU 부담이 큰 작업은 process 기반이 존재함
- 네트워크 확인, 동기화, 문서 단위 오케스트레이션은 thread 기반이 존재함

### 8. 설정은 `ConfigManager`를 통해 읽고, example을 기준으로 관리한다

- 기준 파일은 `config/default.yaml.example`
- 로컬 실행 파일은 `config/default.yaml`
- `default.yaml`이 없으면 example을 복사해 생성
- 새 설정 키를 추가하면 example과 README를 함께 갱신

즉, 설정 스키마 변경은 코드만 바꾸고 끝내지 말고, 문서와 템플릿도 같이 움직여야 합니다.

### 9. 라벨 값은 루트 `label/` 기준표를 우선 사용한다

현재 코드에서는 `load_label_ids`, `load_label_color_map` 같은 공통 로더를 사용해 라벨 값을 읽습니다.

권장 방식은 아래와 같습니다.

- 라벨 값 직접 입력보다 `label/*.xlsx` 기준표 우선
- 라벨 색상, 선택 목록, 표시 규칙은 공통 로더 결과 사용
- 라벨 스키마가 바뀌면 `label/README.md`와 관련 탭 README를 함께 갱신

## 문서 작성 규칙

### 1. README는 가까운 상위 문서를 진입점으로 사용한다

- 루트 `README.md`: 레포 개요와 문서 진입점 안내
- 폴더 `README.md`: 해당 폴더의 목적, 구조, 유지보수 규칙
- 중요하고 반복해서 참조하는 상세 문서만 별도 유지
- 그렇지 않은 설명은 상위 README에 통합

### 2. 별도 README를 둘 기준

아래 중 하나에 해당하면 별도 README를 유지할 가치가 있습니다.

- 독립적으로 계속 커질 가능성이 큼
- 작성 방법이나 확장 방법이 필요함
- 수정 시 영향 범위를 문서로 분리해 설명할 필요가 큼
- 여러 사람이 자주 직접 열어 보게 됨

그 외에는 상위 README에 합쳐서 문서 진입 경로를 줄이는 편이 좋습니다.

### 3. 문서 변경은 동작 변경과 같이 간다

다음 변경이 있으면 README도 함께 업데이트하는 것을 기본 원칙으로 둡니다.

- 설정 구조 변경
- 라벨 기준 변경
- splitter, 상태 메시지, 미리보기 흐름 변경
- S3 쓰기 정책 변경
- 로컬 인증 파일/산출물 위치 변경

## `.gitignore` 관리 규칙

### 1. 전역 규칙은 루트 `.gitignore`

- Python 캐시
- 가상환경
- 전역 IDE 설정
- 공통 비밀 파일 패턴
- 전역 `.cache/`, `outputs/`

### 2. 폴더 전용 규칙은 폴더별 `.gitignore`

아래처럼 특정 폴더에서만 생기는 파일은 해당 폴더 `.gitignore`에서 관리합니다.

- `config/.gitignore`: `default.yaml`
- `app/tabs/raw_data_analysis/.gitignore`: OAuth 시크릿, 로컬 export, 샘플 폴더
- `app/tabs/misc_tools/apps/parse/.gitignore`: 파싱본, 로그, 샘플 예외 관리

### 3. 이미 추적된 파일은 ignore만으로 해결되지 않는다

민감 정보나 로컬 파일이 이미 Git에 올라가 있다면 `.gitignore` 추가만으로는 정리되지 않습니다. 이 경우에는 삭제 또는 untrack까지 함께 처리해야 합니다.

## 공동 작업 체크리스트

코드 변경 후 아래 항목을 같이 점검하는 편을 권장합니다.

1. 변경이 탭 폴더 안에서 끝날 수 있는데 `common/`까지 건드리지는 않았는가
2. 설정 키를 추가했으면 `default.yaml.example`과 `config/README.md`도 갱신했는가
3. 라벨 기준을 바꿨으면 `label/README.md`와 관련 탭 문서도 확인했는가
4. 로컬 전용 파일이나 인증 파일이 생겼으면 적절한 `.gitignore`에 반영했는가
5. S3 쓰기나 데이터 수정이 있으면 스냅샷 비교 기준이 유지되는가
6. 상태 메시지와 진행률 표시는 기존 형식과 크게 어긋나지 않는가
7. 새 폴더를 만들었으면 상위 README 진입 경로도 함께 정리했는가
